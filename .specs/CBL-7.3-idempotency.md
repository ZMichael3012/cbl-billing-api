## 1. Контекст и цель

Контракт 7.1 требует `Idempotency-Key` на всех мутирующих вызовах: повтор с тем
же телом отдает исходный ответ с `Idempotent-Replayed: true`, тот же ключ с
другим телом - `409 idempotency_key_reuse`; кэшируются только успешные ответы,
окно - 24 часа (CBL-003, разделы 2 и 7). 7.3 реализует слой идемпотентности
BFF: быстрый путь Redis (T-02) и источник истины - уникальный индекс
PostgreSQL; сбой Redis не ослабляет защиту (проверка уходит в БД).

## 2. Границы

In scope: миграция `idempotency_keys`, домен отпечатка и валидации ключа,
сервис решений, gin-middleware захвата ответа, Redis-кэш ответов, compose
smoke. Out of scope: конкретные эндпоинты `/v1` (7.4), ретеншен и партиции
(14.2), идемпотентность внутренних gRPC-вызовов (там свои ключи), защита от
перебора ключей (rate limit - 7.5).

## 3. Правила (по контракту 7.1)

- Ключ: заголовок `Idempotency-Key`, обязателен для `POST`; форма
  `^[A-Za-z0-9._~-]{8,128}$`; отсутствие - `400 missing_idempotency_key`,
  битая форма - `400 validation_failed`.
- Отпечаток запроса: `sha256(method + "\n" + path + "\n" + сырое тело)`;
  сравнение по нему различает повтор и переиспользование ключа с другим телом.
  Область ключа (мерчант) в отпечаток не входит: она обеспечена уникальным
  индексом `(merchant_id, key)` и префиксом Redis-ключа. Query-строка не
  участвует: POST мерчант-API 1.0.0 не используют query; при появлении -
  включить `RequestURI` аддитивной правкой контракта (правило для 7.4).
- Поведение: промах - выполнение и (для `2xx`) сохранение снимка ответа;
  повтор того же отпечатка - исходный статус/тело/`Content-Type` плюс
  `Idempotent-Replayed: true`; другой отпечаток - `409 idempotency_key_reuse`;
  ошибки (`>=400`) ключ не занимают (запись удаляется, мерчант повторяет).
  Конфликт переиспользования живет, пока строка не удалена очисткой 14.2
  (контракт не обещает освобождение ключа после окна - осознанно).
- Снимок ответа хранится открытым текстом в PG и Redis: повтор
  `POST /v1/webhook-endpoints` вернет `signing_secret` (контракт), поэтому
  пространства `idem:v1:*` - якорь и конфиденциальности (чтение Redis =
  утечка тел) и авторизации (запись = подделка replay, KI-billing-api-02);
  ACL/сеть до prod (0.6), ретеншен/шифрование при необходимости - 14.2.
- Конкурентный повтор при обработке - `409 idempotency_in_progress`
  (без ожидания в запросе); зависшая запись `processing` старше
  `IDEMPOTENCY_PROCESSING_TIMEOUT` считается брошенной и переобрабатывается.
- Завершение и удаление адресуются идентификатору попытки (fencing):
  устаревшая попытка не может завершить или удалить строку нового исполнения.
- Тело мутирующего запроса ограничено 1 MiB (`http.MaxBytesReader`):
  превышение - `413 payload_too_large` до обращения к журналу.
- Окно хранения `IDEMPOTENCY_TTL` (по умолчанию 24h, 1h - 168h): после
  истечения повтор обрабатывается заново (запись переиспользуется, кэш не
  продлевается дольше остатка окна); очистка пачками - 14.2.

## 4. Хранение

`idempotency_keys`: `id uuid` (UUIDv7), `merchant_id`, `key`, `request_hash
bytea(32)`, `state` (`processing`/`completed`), `response_status`,
`response_content_type`, `response_body` (до 256 KiB, см. §7), `created_at`,
`completed_at`; `UNIQUE (merchant_id, key)`. Второй барьер: триггер
`idempotency_guard` - неизменяемы `id`/`merchant_id`/`key`/`request_hash`/
`created_at`, переход только `processing -> completed`, завершенная запись
неизменяема (удаление разрешено: это транзитный журнал). Redis-кэш:
`idem:v1:{merchant}:{key}` -> JSON `{hash, status, content_type, body_base64}`
с TTL `IDEMPOTENCY_TTL`; источник истины - PG, при ошибке кэша решение
принимает БД.

## 5. Функциональные требования

FR-1. `Begin(merchant, key, fingerprint)`: Redis-хит валидируется (хэш, статус
2xx, тело, срок) - валидный реплей; порча, подмена хэша или истечение дают
промах (решение принимает PostgreSQL, оракула 409 по кэшу нет). Промах -
PostgreSQL: отсутствие записи - вставка `processing` и `Proceed` (с id
попытки); гонка вставки (уникальный индекс) - повторное чтение; `completed`
свежий - `Replay` (+ остаток окна в кэш); `completed` старше TTL - удаление
конкретной попытки и `Proceed`; `processing` свежий - `Conflict(in_progress)`;
`processing` старше таймаута - удаление и `Proceed`; конкурент между
delete+insert разрешается повторным решением (глубина не более 2).

FR-2. `Finish(attemptID, snapshot)`: для `2xx` - `Complete` конкретной попытки
(fencing по id) и запись в Redis с остатком окна; для `>=400` или overflow -
удаление конкретной попытки `processing` (устаревший Finish не трогает строку
нового исполнения); сбой `Complete` - WARN и best-effort запись в Redis;
фиксация выполняется на контексте без отмены клиента (бюджет 5 с).

FR-3. Middleware `httpmw.Idempotency`: применяется только к `POST`;
захватывает тело запроса (восстанавливает для обработчика, предел 1 MiB) и
ответ (статус/заголовок типа/тело); дубли заголовка `Idempotency-Key`
отклоняются (`400 validation_failed`); `GET` и другие методы не трогает;
ответ-реплей несет `Idempotent-Replayed: true`; `400`/`409`/`413` -
problem+json без деталей внутреннего состояния.

FR-4. Конфигурация fail-fast: `IDEMPOTENCY_TTL` (24h),
`IDEMPOTENCY_PROCESSING_TIMEOUT` (2m, 30s - 15m); невалидные значения - отказ
старта; Redis опционален (при отсутствии - только PostgreSQL, WARN).

FR-5. 7.4 (правило владельца контракта): downstream-вызовы получают
производные ключи идемпотентности `f(merchant, Idempotency-Key, шаг)` (например
`{merchant}:{key}:create_payment`); при ошибке композиции ключ освобождается,
а повтор обязан переиспользовать те же производные ключи, чтобы не создать
дубли в Payment/Ledger/Payout.

## 6. Тесты

- unit: форма ключа и отпечаток (стабильность, различие тела/пути/метода);
  матрица `Begin` (промах и вставка, гонка, replay кэша и БД с остатком окна,
  reuse, TTL, processing свежий/зависший, подмена/порча/истечение кэша -
  деградация в БД без оракула 409); fencing (поздний Finish устаревшей попытки
  не завершает и не удаляет строку нового исполнения); `Finish` (complete+кэш,
  abort, сбой complete, overflow); middleware (нет/дубль заголовка, битая
  форма, не-POST, реплей-заголовок, предел тела 413, overflow-ответ, 503).
- integration (testcontainers PostgreSQL + Redis): уникальный индекс (именованный)
  и второй барьер (immutable, completed неизменяем, возврат 500-снимка
  отклоняется CHECK, прямой INSERT completed отклоняется); снимок ответа;
  удаление по попытке и состоянию; middleware поверх httptest с реальными
  PG+Redis: первый POST выполняет обработчик, повтор - реплей без повторного
  эффекта (счетчик), другое тело - `409`, ответ `>=400` не кэшируется,
  конкурентный повтор - один запуск обработчика.
- e2e compose (`test/e2e/api_keys.ps1`): keyctl-сценарий 7.2 плюс smoke
  сервиса (профиль app): сборка по services-контексту, `readyz`, миграции
  версии 2; отклонение от буквального HTTP-сценария зафиксировано: реальных
  маршрутов `/v1` до 7.4 нет, middleware проверяется integration-сценарием с
  реальными PG+Redis (прецедент CBL-5.1, раздел 9), риск закрывается 7.4.

## 7. Edge cases

Тело запроса читается один раз и восстанавливается для обработчика, предел
1 MiB (`413 payload_too_large`); тело ответа больше 256 KiB - снимок не
сохраняется (WARN, попытка удаляется: повтор выполнится заново); сбой Redis на
любом шаге - решение по БД (подмена/порча/истечение значения - промах);
поздний Finish устаревшей попытки не трогает новую (fencing по id); фиксация
выполняется без отмены клиента (дисконнект не теряет снимок); `processing`
после падения процесса истекает по таймауту (паника обработчика освобождает
попытку); повтор после истечения TTL выполняется заново; дубли заголовка
отклоняются; ключ валидируется до обращения к хранилищу; заголовок
`Idempotency-Key` на неподдерживаемом методе игнорируется.

## 9. Нефункциональные требования

Горячий путь 7.4: хит Redis не касается БД; промах - один SELECT/INSERT по
именованному уникальному индексу `(merchant_id, key)`; транзакции короткие
(вставка до обработчика); тела запроса ограничены 1 MiB, снимки ответов -
256 KiB; снимок не логируется, но хранится открытым текстом в PG и Redis
(включая `signing_secret` повторов регистрации вебхуков): пространства
`idem:v1:*` - якорь конфиденциальности и авторизации (KI-billing-api-02,
ACL 0.6, ретеншен 14.2); P95 без Redis - бюджет одиночного INSERT/SELECT.

## 10. Ревью (CBL-001, шаг 6)

## 11. Открытые вопросы

- Ретеншен и партиционирование `idempotency_keys` - 14.2 (KI-billing-api-06):
  окно обеспечивается проверкой TTL; строки растут.
- Аддитивные коды `idempotency_in_progress`, `missing_idempotency_key`,
  `payload_too_large` не входят в каталог 7.1: внести в `billing.v1.yaml`
  при финализации 7.4/15.4 (перечень кодов аддитивен).
- Ожидание завершения конкурентного запроса (вместо мгновенного 409) - при
  появлении требования из 7.4 (KI-billing-api-07).
- Снимки открытым текстом (включая `signing_secret` регистрации вебхуков):
  шифрование/укороченный TTL для секрет-содержащих ответов - при требовании
  безопасности (13.x) до prod-выкладки.
- Реальный HTTP-e2e middleware (порядок Require -> Idempotency в main) -
  7.4, вместе с первыми маршрутами.
